# Agent Temp Manager 0.3.0: release notes (release candidate, NOT published)

**This is a release candidate. It is not published:** there is no tag `v0.3.0` and no GitHub Release. Only the
maintainer's explicit approval publishes a version, and only through its GitHub Release. The latest published version
is [0.2.0](https://github.com/JohnHck/agent-temp-manager/releases/tag/v0.2.0). Portuguese:
[V0.3.0-RELEASE-NOTES.pt-BR.md](V0.3.0-RELEASE-NOTES.pt-BR.md). Candidate record: [V0.3-RC.md](V0.3-RC.md).

## What it is

Read-only auditing, preview and runtime diagnostics of the temporary directories that AI coding agents leave on Windows,
across every local user profile. V0.3 builds and tests, behind the closed deletion gate, the safeguards a human-approved
real cleanup needs.

**Real deletion is disabled in every copy of this version.**
- `agent-temp clean` still runs every safety gate and prints the exact plan, then stops without deleting anything
  (`EXCLUSAO_REAL_DESABILITADA_V0_1`, the code is kept for compatibility).
- No option, environment variable or configuration file enables deletion.
- `ORPHAN_SUSPECTED` stays informational only: no class or category authorizes deletion.

## What changes for users (deletion gate closed: every copy)

- **New category in preview, audit and the TUI:** `ELIGIBLE_WITH_DECLARED_RISK`. It applies to a Claude Code session
  root of the own profile that would otherwise be eligible except for incomplete process coverage (B1), when the token
  is not elevated, the class is `ORPHAN_SUSPECTED` without flags, and there is no other refusal of any kind. It is shown
  as **not released**. It never appears as `ELIGIBLE`, and with the gate closed nothing can act on it.
- **New command `agent-temp authorize -Path <root> -RecordFile <new file>`** (AUT-1). It records the operator's discard
  authorization of one root, bound to the plan shown:
  - three typed confirmations, in an interactive console only;
  - the plan is presented again and compared before the record is written;
  - a new file, created through the pinned writer.

  **It deletes nothing, nothing in the product reads it, and it makes nothing eligible.** The technical result, B1 and
  RECENT included, is recorded apart from the declarations. Details: docs/USAGE.md, "Discard authorization".
- **The V0.2 runtime evidence enters preview and the clean plan** (B2-1). A root's observed use or live session blocks
  it. Ambiguous relations, unverified sessions and failed or timed-out collection need investigation. The evidence can
  only make a root stricter, never eligible, and the absence of evidence is not evidence of non-use.
- **`clean` options:** `-AcceptB1ResidualRisk` exists and has **no effect** with the gate closed. `-LogFile` is still
  checked against the audited directories before the plan; with the gate closed no log is required, created or opened.
- **The product contract changed:** "incomplete process coverage always blocks deletion; there is no override" becomes
  "it blocks, except one narrow, explicit exception". That exception is reachable only past the deletion gate, so no
  copy of 0.3.0 reaches it. See docs/SECURITY-MODEL.md, gate 6.

## Built and tested, inactive in every copy (past the deletion gate only)

None of the following can run in a copy of 0.3.0. Each one is exercised only by the test suite, with the gate opened
inside its own process, and by the CI-only harness on disposable VMs.

- **T1, clean log (F-04).** A new file per run, required once deletion is enabled. It is written through a handle kept
  for the run: append-only, flushed per record, JSON Lines. Each root gets an `intent` before the deletion and a
  `result` after it.
- **B8, one clean at a time.** The machine-wide mutex `Global\AgentTempManager.Clean` is taken without waiting, before
  any inventory, and released last. The verified native library is loaded before it (fix F-E).
- **AUT-2, confirmation bound to the plan.** Per root of the executable set, the task and the content decision; then
  `APAGAR <N> CAMINHOS <plan id>` for the exact set. A plan check refuses any change during the questions, and a
  revalidation refusal stops the run (`REVALIDATION_REFUSED`).
- **B1 restricted exception.** It acts only through `clean -AcceptB1ResidualRisk`, one root per run, with a per-root
  `ACEITO RISCO B1`. The identities of the processes not inspected are bound to the plan id, and a new one refuses.
  Residual risk declared, no rollback.

## Validation (V2 and V3, CI on disposable VMs)

Windows Server 2025 and 2022, and Windows 11 ARM64, each with the installer under Windows PowerShell 5.1 and
PowerShell 7. The installed engine runs with the gate opened only in the harness's own process memory: real deleter,
real log file, real lock and real revalidation. Every confirmation is automated by the harness and is **never a human
acceptance**.

- **V2, the real clean end to end.**
  - As a standard user (B1 exception): one root deleted, with the log read back and the lock seen busy from another
    process.
  - Elevated: `ELIGIBLE` was unreachable, because the process coverage measured incomplete on every runner. Those cases
    are NOT TESTED; nothing was forced.
- **V3, attacks in each window of the flow:** reparse points and links; files and folders in use; new entries and
  changes; a third-party ACL; new processes; deleter outcomes; the log; a run that ends inside itself; concurrency; and
  shared bases.
  - Each case asserts its own code, the log read back from the file and the number of calls to the deleter.
  - Each case also checks that nothing outside the planned root changed.

Details: docs/TESTING.md, "V3 as a whole".

## Measured findings

- **Process churn.** Under the B1 exception, any new process that cannot be inspected appearing between the plan and
  the deletion refuses the root (`PLAN_CHANGED_BEFORE_EXECUTION` or `REVALIDATION_REFUSED`). This is fail-closed, and
  nothing is deleted. On the runners 1 to 7 new identities appeared between two collections, so some runs needed a
  repetition.
- **Elevated coverage stays incomplete.** Protected processes are not inspectable, so `ELIGIBLE` was not reached in CI.
  The only deletion path proved is the B1 exception: own profile, not elevated, one root.
- **The abandoned-lock signal is opportunistic.** `CLEAN_LOCK_ABANDONED` appears only while another handle keeps the
  lock object. Otherwise the next clean simply acquires the lock, and an `intent` without a `result` in the log is the
  only trace of the interruption.

## Declared limits

**Not tested, by design or by decision:**
- a write that keeps every statistic (there is no content hash);
- a real exception inside the deleter (it reports codes; it does not throw);
- a real failure of the log write (no size-limited volume on the runners);
- an interruption in the middle of the tree (no per-file hook, no forced termination);
- a base claimed by two accounts (the other account's environment was not readable);
- the elevated leg's in-deleter cases, while its coverage is incomplete;
- the CLI and the TUI past the gate.

**Proved limits** (docs/SECURITY-MODEL.md). In each of them nothing outside the planned root is affected.
- A handle with no data access and full sharing is invisible to the lock probe. It leaves a partial deletion or an
  unconfirmed absence.
- A process can start with its working directory in a pinned folder, and the folder is still deleted.
- The ACL is not read again once the tree is pinned.
- A hard link to a file outside the root loses only the name inside the root.

**Unchanged from 0.2.0:**
- process working directories are not observable;
- handles with full sharing are not observed;
- F-05 (attribution of a TEMP shared by two users; cleanup stays blocked) and F-14 (`verify` does not report unlisted
  files outside `providers`) are deferred.

F-04 is implemented by T1. It counts as fixed only once a version with it is published.

## What remains blocked (closed gates in every copy)

No option, environment variable or configuration file opens them. Source, package and installation are checked.

- Real deletion (`AtmRealDeletionEnabled = $false`).
- Real Git worktree diagnostics (`AtmWorktreeDiagnosticsEnabled = $false`).
- Real open-file (handle) diagnostics (`AtmHandleDiagnosticsEnabled = $false`).
- The diagnose JSON export (`AtmDiagnoseExportEnabled = $false`).

## Install and verify (after publication)

1. Download `agent-temp-manager-0.3.0.zip` and `SHA256SUMS.txt` from the GitHub Release `v0.3.0`, once it exists.
   Compare `(Get-FileHash .\agent-temp-manager-0.3.0.zip -Algorithm SHA256).Hash` with `SHA256SUMS.txt`.
2. Extract into a folder that only administrators can write (for example under `%ProgramFiles%`).
3. From an elevated PowerShell started with `-NoProfile`, run `install\Install-AgentTempManager.ps1` for a new
   installation, or with `-Update` over an earlier installation ([docs/INSTALL.md](../INSTALL.md)). The update from the
   published 0.1.0 and 0.1.1 is tested in CI. The update from the **published 0.2.0 is NOT TESTED yet**, and it is a
   publication blocker (V0.3-RC.md).
4. In a new terminal: `agent-temp verify`, then `agent-temp version`, which shows `0.3.0`.
