## C. ARM64 with PowerShell 7

* **Measured, not inferred.** The probe "Ambiente :: FINAL-B: custo de processos filhos" ran over four CI rounds. It times cmd, Windows PowerShell 5.1, the installed launcher, the launcher with a minimal environment, the launcher's loading sequence step by step inside the child, and a bisection over the inherited environment.
* **Results:**
  * the launcher takes about 1 s with a Windows PowerShell 5.1 or AMD64 PowerShell 7 parent, and about 23 s with the ARM64 PowerShell 7 parent;
  * with a minimal environment it takes 12–25 s on every runner;
  * the whole cost is in the child's first command, before any product code (the libraries load in about 0.3 s);
  * the bisection isolates `PSModuleAnalysisCachePath`: without a usable module analysis cache, a fresh Windows PowerShell 5.1 spends that time in command discovery;
  * with the ARM64 PowerShell 7 parent the inherited variable is present and its file exists, but the child is still slow;
  * a private cache for the child does not help (the second run is as slow as the first).
* **Cause of the ARM64 slowness:** about 142 launcher calls in R-B5 verify × ~22 s of PowerShell's own module analysis per child.
  * It is a runner/PowerShell environment effect, not a deadlock and not product logic.
  * Why the ARM64 PowerShell 7 image's cache is unusable for the child is not determined.
* **Earlier hang** (ARM64 Windows PowerShell 5.1, R-B5 verify region, no output for 44 minutes, before FINAL-B):
  * the cause is not determined, and it has not recurred in the later runs;
  * R-B5's CLI calls now run as child processes inside their own Job Object (FINAL-B-S, section L), with a 180 s deadline and a sanitized `CHILD_TIMEOUT` code;
  * a recurrence now fails the case instead of hanging the job.
* **Full suite:** not run, because the bounded-time requirement cannot be met (R-B5 verify alone ≈ 52 minutes there).
* **What runs instead:** ARM64 PowerShell 7 runs the suite without the launcher-heavy cases (`-Except`; 40-minute bound; the excluded cases are printed in the log; still labelled `SUBCONJUNTO`). The exclusions follow measured times on that runner (earlier run, before FINAL-B), not whole areas:

## G. F-10: deletion engine against a disposable tree

* **Case "Gate V0.1 :: FINAL-B F-10".** It runs the native engine only, on a tree the harness creates. Every junction points to a sentinel folder inside the sandbox.
* **The four checks:**
  1. An empty pinned folder turned into a junction inside the window, through the existing `afterPinning` test hook and another handle (FSCTL, the M-1 limit): `PINNED_DIR_CHANGED`, and the sentinel is unchanged byte for byte.
  2. A junction present before the start: `REPARSE_POINT_FOUND`, nothing deleted.
  3. A junction ancestor: `ANCESTOR_REPARSE_POINT`.
  4. Renaming a pinned folder during the window: refused by the system, after which the engine deleted exactly the disposable tree.
* **Final path by handle:** a separate case, "FINAL-B F-10: verificacao do caminho final por handle". A tree reached through a `subst` drive letter is refused with `ROOT_PATH_REDIRECTED` and nothing is deleted. It is NOT TESTED where no drive letter is free.
* **Gate:** the distributed gate is checked in the shipped file: a single `$false` assignment.
* **Result:** PASS on L and on every CI runner. Nothing outside the authorized tree was deleted, so the stop rule was not triggered.
* **Why a junction cannot be followed:** a deletion through a handle opened before the conversion marks the reparse-point folder itself, never its target.
* **Residual:** the deletion gate stays closed; it is not opened by this record.

## J. F-04 and F-05 (analysis, nothing changed)

* **F-04** (`clean -LogFile` appends by name):
  * **Proposal:** open the log once, before the first deletion, through the pinned writer, and keep the handle for the whole run (writes through that handle, never by name again).
  * **Effect:** `-LogFile` changes from "append to an existing file" to "a new file per run". That is an incompatible public change.
  * **Compatible alternative:** keep append, but open the existing file once with the pinned chain and a handle-relative open (no `FILE_CREATE`), refuse a reparse point or a hard link at the name, and hold the handle.
  * Latent while the deletion gate is closed. A maintainer decision, before the gate can ever open.
* **F-05** (a TEMP value naming another user's folder):
  * **Proposal:** attribute a base to a profile only when the folder's owner is that profile's SID, or SYSTEM/Administrators for a shared machine folder. Otherwise it becomes a discovery gap with a code, and `SHARED_TEMP` partitions stay blocked as today.
  * **Effect:** V0.1 attribution changes in that case only (the audit shows a gap instead of the first claimant); deletion stays safe either way.
  * **Shared folders** (`%WINDIR%\Temp`) keep their current rule.
  * Needs a HUMAN_GATE because it changes V0.1 output.

## L. FINAL-B-S: test process executor

* **Maintainer gate:** the FINAL-B helper `Stop-AtmTestChildTree` chose descendants by `ParentProcessId` from a
  global `Win32_Process` enumeration and called `Kill()` on PIDs, accepting one second between creation times. That
  is not a proof of identity against PID reuse. The asynchronous reads could also wait without limit while a
  descendant held the output pipe.
* **Removed:** no enumeration, no PID, no tree reconstruction and no `Kill()` remain in the executor.
* **Now:** `Invoke-AtmTestChild` runs every child through `AgentTempManager.AtmJobRunner`, the Git runner's executor
  (src\lib\Native.cs):
  * the Job Object is created and its limits are set and read back before the process exists;
  * the process is created inside the job (`PROC_THREAD_ATTRIBUTE_JOB_LIST`), never started outside and associated
    later; `cmd.exe` comes from its absolute path, with an explicit environment and working directory;
  * output is read to the end, so the child never blocks; at most a cap is kept per stream (4 MB by default), and
    truncation is declared (`[SAIDA_TRUNCADA]`);
  * on the deadline, or when a member still holds the pipes after the child ended, only the job's members are
    terminated (`TerminateJobObject`; `KILL_ON_JOB_CLOSE` when the job closes).
* **Bound:** the deadline plus the runner's fixed waits, at most about 22.5 s (10 s for the child after termination,
  2.5 s for the pipes, 10 s for the readers). A member cannot leave the job (no breakaway). Reader threads still
  alive after those waits are abandoned without being waited on. These are the implementation's limits, not a
  promise of shorter times.
* **Failures:** a sanitized `CHILD_RUNNER_<code>` (job, limits, attributes, pipes, process creation, invalid limits),
  raised before anything runs when the job or the process cannot be set up. A failed job termination is
  `CHILD_RUNNER_JOB_TERMINATE_FAILED` (FAIL), with no fallback to a PID search. The return contract keeps `Exit`,
  `TimedOut`, `Text` and `Ms`; `Truncated` and `JobTerminated` are added.
* **Negative tests** ("Executor :: FINAL-B-S", in every job including ARM64 PowerShell 7):
  * normal exit;
  * long stdout and stderr, truncation declared;
  * child past the deadline (`CHILD_TIMEOUT`, job terminated within the bound);
  * a descendant still holding the pipe after the child ended, and a descendant past the deadline: each terminated
    as a job member. A read-only check of the descendant's own record (PID and creation time written by itself)
    shows it gone; this check is never used to signal anything;
  * a sentinel process created by the harness outside the job, a moment before the child: it stays alive and ends by
    itself;
  * runner failures, real and synthetic: invalid limits, a process that cannot start inside the job, every job and
    attribute error, an unexpected reason (sanitized), a failed termination;
  * a static check that the executor has no PID lookup, enumeration or kill;
  * regressions: R-B5, F-10, installation, the ARM64 probe, artifact privacy.
* **Clean environment:** the private-TEMP run stays recorded at `9851acb` (section B). It was not repeated on the new
  head, and no new folder was created.
