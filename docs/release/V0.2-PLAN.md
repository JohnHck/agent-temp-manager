## Scope and limits

* In scope: the V0.2 deliverables of the roadmap (processes, services, resources, virtualization, Git worktrees,
  dependencies, temporary directories extended with runtime evidence, `diagnose` command, TUI view, JSON export,
  identity and elevation display, Claude Desktop provider) and the V0.1 commitment carried into V0.2 by
  `SECURITY-MODEL.md` (*Discovery visibility*: injectable registry sources and a visible note when profile discovery
  is incomplete).
* Out of scope: V0.2.1 (desktop GUI and live monitoring), V0.3 (real deletion), any change to the V0.1 gates,
  classification or deletion code, enabling the release gate, a remote check of publication (may come later as an
  explicit option; never implicit).
* Read-only, always: no deletion, move, rename or modification of user files; no Git fetch, pull, prune, gc, checkout,
  stash or index-writing command; no change to ACLs, services, processes, virtual machines, scheduled tasks or Windows
  configuration; no elevation requested; no network access. The only process the engine may terminate is a Git child it
  started itself, inside its own job object, on timeout (decision D-4).
* Bounded, always: time, files, memory and processes have limits; a timeout or read failure gives `UNKNOWN`/`PARTIAL`,
  never clean (ADR-0001).
* Privacy: no command lines, environment values, tokens, Git configuration values, service command-line arguments or
  file contents are printed or exported.
* Process: small pull requests, full suite on Windows PowerShell 5.1 and PowerShell 7, commit identity check, privacy
  scan, static analysis; noreply commit identity; fast-forward merges of the validated head; no force-push; no bypass
  of branch protection. Merges and releases only with the maintainer's explicit authorization.
* Version: `$script:AtmVersion` stays `0.1.0` until the release-candidate pull request of the FINAL phase sets
  `0.2.0`; until then `main` is development code, not a release.

## Stop conditions (HUMAN_GATE)

V0.1 gate; a decision listed below that is still open when its phase starts.

## Test strategy

* **Isolation:** every write happens in the suite's sandbox (`%TEMP%\atm-tests-<random>`). Git fixtures are created
  there with an isolated configuration (`GIT_CONFIG_GLOBAL` pointing to a sandbox file, `GIT_CONFIG_NOSYSTEM=1`,
  fixed fictional author identity, no remotes except local sandbox paths). The suite never runs Git, the diagnose
  engine or any collector on a real repository, worktree or project of the machine it runs on.
* **Fixture creation vs engine:** only the test code may run mutating Git commands, and only on sandbox fixtures; the
  engine's runner refuses them (allow-list) and the runner spy records every call made by the engine.
* **Mocks:** every collector has an injected source; fixtures are small PowerShell objects with fictional names, PIDs,
  SIDs (`S-1-5-21-1-2-3-...` style) and paths (`C:\Users\alice\...`), never real data.
* **Read-only proofs:** before/after listings with SHA-256 of fixture trees (including `.git\index`), services'
  state snapshot on the real machine, and the existing audit/preview sandbox comparison.
* **Real-machine tests (read-only):** process and service listings of the suite's own session, identity and token
  elevation type; results recorded as observed, never assumed.
* **Native code:** child processes started by the suite inside the sandbox (working directory, held files, 32-bit
  child where available) to exercise ADR-0004 and the bounded runner; nothing outside the sandbox.
* **Both shells and both languages** for every new test area; `NAO_TESTADO` is never counted as a pass.
* **Heavy tests** (1,000+ real worktrees, large trees) behind `-SkipHeavy`; light synthetic equivalents always run in
  CI. A manual CI job (`workflow_dispatch`) for the heavy set is added in P3-E if run time allows.
* **Destructive or heavy experiments** (for example a lazy-fetch or ownership scenario that needs another account) run
  only on disposable CI runners or VMs, never on the maintainer's machine.

## Risks

| Risk | Mitigation | Rollback |
|---|---|---|
| A Git command writes to a repository | Allow-list, `--no-optional-locks`, `GIT_OPTIONAL_LOCKS=0`, read-only proofs with SHA-256 of `.git` on every fixture | Revert the pull request; the engine never ran on real repositories in tests |

R-B5 security fix (isolated PR, before P1-B4-b; merged only with the maintainer's authorization):

* **Launcher:** one integrity check, computed with .NET before any product code is loaded, serves `verify` and every
  other command. Exit code 5 for a listed file missing or altered, a launcher-loaded library or a provider not
  listed, a malformed manifest or an invalid entry (absolute path, `..`, duplicate, malformed hash), and an installed
  copy (`install-state.json`) without a manifest. A listed file that cannot be read, or a `providers` directory
  that is missing or cannot be listed, is the same refusal (exit code 5, reported by relative name only, no
  exception text); an unexpected failure of the check itself refuses an installation too. `verify` prints every problem and loads nothing when one exists;
  when every file matches, it loads only the verified catalog for its localized summary. `verify` now also reports
  an unlisted provider (exit code 5), as every other command already refused it. Exit code 4 stays for a source
  checkout.
* **Administrative bootstrap:** `install/InstallCommon.ps1` dot-sources `lib\I18n.ps1` only after its SHA-256 matches
  the package's `src\manifest.json` or, for uninstall and rollback, the installed copy's manifest; a package
  without a manifest is loaded unverified only with `-SourceWithoutManifest` (and by the release build of the
  repository); otherwise built-in bilingual texts are shown. A catalog from another `-SourceDir` is never executed.
* **Rollback:** `<InstallDir>.previous` is checked in the installer's process before anything moves; the current copy
  is removed only after the restored one passes `verify`, and both are put back when it fails or throws. If putting
  them back fails too, nothing more is moved or deleted and the error names where each copy is.
* **Tests (disposable copies, harmless markers):** every launcher-loaded library and the provider removed, altered,
  or shadowing `Get-FileHash`; a planted provider; eight invalid-manifest cases; an installed copy without a
  manifest; the catalog altered in the package, in another `-SourceDir` and in the installed copy, with and without
  explicit authorization; the three administrative scripts; rollback to an altered `.previous`; unreadable
  libraries, provider and manifest (exclusive handle), a missing `providers` directory and a broken junction in its
  place; a hidden provider, unlisted (refused) and listed (still loaded, never silently left out); a post-swap `verify` that fails or throws, and an undo blocked by an open file. Each asserts the
  exit code and that no marker was written.
* **Residual:** no authenticity against an administrator who can change the launcher and the manifest; a file
  could change between its hash check and its load (inside the administrator-only directory); `install\*.ps1` are
  covered only by `SHA256SUMS`; source checkouts have no integrity guarantee.

R-B6 fix, update atomicity and recovery (isolated PR, before P1-B4-b; merged only with the maintainer's
authorization):

* **Before anything moves:** the source is validated as before (required files, syntax, manifest, SHA-256, exact
  file set), the staged copy gets its native assembly, manifest and ACL check, and now also runs its own `verify`.
  Any failure removes only the staged copy; the installation and `.previous` are untouched.
* **Swap:** an existing `<InstallDir>.previous` is set aside in `<InstallDir>.recovery-<8 hex>` instead of being
  deleted; the installed copy becomes `.previous`; the staged copy takes its place.
* **After the swap:** the PATH change, the state write, the ACL check and `verify` are one guarded block. On a failure
  or an exception the failed copy is moved out, the installed copy and the older `.previous` go back, a PATH entry
  added by this run is removed again, and only then is the failed copy removed. The older `.previous` is discarded
  only after the new version verified.
* **Failed recovery:** if putting the copies back fails, nothing more is moved or deleted; the error names where each
  copy is and how to rename them back. The same applies to rollback: the retired copy is a recovery directory, and
  a swap whose reversal also fails reports both positions instead of a raw error.
* **Pending transaction:** update and rollback write `<InstallDir>.transaction.json` (operation, state, where each
  copy is) before the first rename; it is removed only once the operation completed or every copy is back, and
  rewritten with the actual positions when the recovery fails. It covers the case with no recovery directory (a
  first update without `.previous` whose reversal fails). If it cannot be written, nothing moves. A `.previous` alone
  is normal and never taken as a failure.
* **Recovery directories:** `<InstallDir>.recovery-*` may hold the only intact installation. While the transaction
  file or a recovery directory exists, update, rollback and **uninstall** refuse before changing anything (the three
  scripts check it before creating their private TEMP; uninstall before the PATH, the product directories and the
  sweep of intermediate copies). `-Update` with no installation but a `.previous` is refused and names the
  `.previous`.
* **One operation per installation (mutual exclusion):** install, update, rollback and uninstall of one `InstallDir`
  take `<InstallDir>.lock`, an exclusive handle (`FileShare.None`, delete-on-close) opened in the administrator-only
  parent, before the first change (the scripts before their private TEMP; `Install-AtmProduct` right after the
  read-only source validation). A second operation cannot open it and refuses with nothing changed; other
  destinations use other files and are not blocked. Chosen over a named mutex because it needs no `Global\` namespace
  privilege, works across sessions and in Windows PowerShell 5.1 and 7 (a .NET `FileStream`), has no thread
  affinity, and aliases of the same path (8.3, case) reach the same file. The OS closes the handle when the holder
  ends, abruptly too, so the lock never outlives its process and is never removed by another operation (no
  `FileShare.Delete`); the persistent evidence of an unfinished operation stays the transaction marker, created with
  `CreateNew` (never overwrites another transaction's marker) and rewritten or removed only by the transaction whose id
  it carries. Limits: only this installer's V0.2 scripts take the lock (a V0.1 script run at the same time is not
  excluded); a holder that hangs keeps others refused until it ends; a missing parent directory is refused
  (nothing to protect, nothing created); filesystems without Windows sharing semantics are not supported.
* **Recovery messages:** built into `install/InstallCommon.ps1` (bilingual, ASCII), never taken from a message
  catalog: an installed catalog may be older (V0.1 has none of these keys) and must not drop the reason, the copy
  positions, the pending state or the instruction not to uninstall. Verified with the real V0.1.0 catalog (scratch)
  and, in the suite, with a catalog stripped of every recovery key.
* **Normal failure versus abrupt interruption:** a failure or exception inside the installer is recovered in
  process. A run killed abruptly (power loss, terminated process) is not recovered: the next run finds the
  transaction file (or a recovery directory, or a missing installation with a `.previous`) and refuses, and an
  administrator decides by renaming and then deleting the transaction file. Two directory renames are not atomic
  together; no atomicity across an interruption is promised. A run killed after the new version verified but before
  the file was removed also leaves it: the next run refuses until an administrator checks and deletes it.
* **Unchanged:** ACL rules, manifest and SHA-256 checks, PATH handling (REG_EXPAND_SZ), the private TEMP, uninstall
  of the product directories. A first installation keeps the V0.1 behaviour (nothing to put back). An installation
  made by V0.1 updates and rolls back with this code; a V0.1 `.previous` restores (cross-version check).
* **Tests (sandbox, test PATH key, no ACL change):** intact update with and without a `.previous`; altered source;
  post-swap `verify` failing and throwing (installed copy and older `.previous` back, PATH as before the run);
  recovery blocked by an open file at the first and the last step (nothing deleted, positions reported, update and
  rollback refused); `-Update` with only a `.previous`; rollback whose swap fails, with and without its reversal
  failing; uninstall refused with a pending recovery (installation, `.previous`, recovery copy, intermediate copies
  and PATH untouched) and working once it is resolved; a first update without `.previous` that succeeds, that fails
  and is recovered, and whose reversal fails at its first or its next step (pending marker; update, rollback and
  uninstall refused; manual recovery lets the update run again); recovery messages with a catalog stripped of every
  recovery key, in a child process; concurrency between independent processes with a gate (the holder writes a
  ready file and waits for a go file): update+update, update+rollback, update+uninstall, rollback+uninstall,
  rollback+rollback, uninstall+rollback, first install+first install on one destination (the second refuses with
  nothing changed), other destinations proceeding meanwhile, an exception in the holder (and in the same process)
  releasing the lock, and a holder killed after the swap (lock released with the process; marker, copies and PATH
  preserved; later operations refuse); another transaction's marker neither overwritten nor removed.
