# Agent Temp Manager 0.1.1: release notes (security fix)

Publication of this version is the GitHub Release `v0.1.1`, created only with the maintainer's explicit approval.
Verify the zip against the `SHA256SUMS.txt` attached to that release before installing. Portuguese:
[V0.1.1-RELEASE-NOTES.pt-BR.md](V0.1.1-RELEASE-NOTES.pt-BR.md).

0.1.1 is a corrective release of 0.1.0 with two security fixes and nothing else: no new command, provider or
capability. **Real deletion stays disabled** (`agent-temp clean` is still plan only, `EXCLUSAO_REAL_DESABILITADA_V0_1`).

## Fixed

* **F-01 (MEDIUM, CVSS 3.1: 5.0): paths from other users' environment are checked before any file API.** A `TEMP`, `CLAUDE_CONFIG_DIR`
  or `CLAUDE_CODE_TMPDIR` value set by another local user in a network or device form (UNC, `\\?\`, `\\.\`, WebDAV) or on
  a network drive letter is no longer passed to file-system calls, so an elevated audit no longer contacts a host chosen
  by that user. Such a TEMP base is reported as `INVALID` (its raw value shown with control characters replaced); such
  a configuration folder is not read and the session evidence of that profile is marked unreadable (a coverage gap,
  never "no sessions"). Path normalization no longer traverses a reparse point, and another user's configuration
  folder reached through a reparse point is not read; your own is read as before.
* **F-02 (MEDIUM): `audit -ExportJson` can no longer be redirected by swapping a folder.** The destination folder and
  its ancestors are opened and held by handle (no reparse point, no redirection, cannot be renamed or replaced while
  held), the V0.1 rules are checked again inside that window, and the file is created relative to the held folder:
  new file only, never through a reparse point, with a protected DACL, and verified through its handle before anything
  is written.

## Severity and evidence

F-01: `CVSS:3.1/AV:L/AC:L/PR:L/UI:R/S:U/C:H/I:N/A:N` (5.0 MEDIUM), based on the demonstrated impact.
The proposed 7.9 HIGH scenario depends on NTLM relay and additional integrity and changed-scope impacts that have
not been demonstrated; it is not the assigned severity.

F-02: `CVSS:3.1/AV:L/AC:H/PR:L/UI:R/S:U/C:N/I:H/A:H` (6.0 MEDIUM). The potential to create or truncate a file
was identified in the 0.1.0 code (`-MustNotExist` followed by `WriteAllText`), not demonstrated dynamically.

## Behaviour changes

* `audit -ExportJson` is stricter. In addition to the V0.1 rules (new absolute file, outside the audited directories,
  no reparse point in the path), it refuses: a file directly in a volume root, a folder path of 240 characters or more,
  a network or non-fixed drive, a `subst` drive letter, and a folder changed while it is being created. A refusal
  prints its code before the V0.1 message and still exits with `10`. A refusal after the file was created says that an
  empty or partial file may remain; it never claims that no file was created.
* The exported file gets a protected DACL (its owner, SYSTEM, Administrators). A file exported from an elevated
  session may therefore not be readable by the same user unelevated.
* Another user's `TEMP`, `CLAUDE_CONFIG_DIR` or `CLAUDE_CODE_TMPDIR` in network or device form, or on a mapped drive
  letter, is now a coverage gap instead of being read. A profile path or profiles directory in such a form (set by an
  administrator in the profile list) is not normalized either.

## Not changed by 0.1.1

Everything else behaves as in 0.1.0. Known limits that 0.1.1 does **not** address are listed in
[SECURITY-MODEL.md](../SECURITY-MODEL.md) and in the 0.2 audit (`docs/release/V0.2-SECURITY-AUDIT.md` on `main`):

* the lexical F-01 check accepts a local path whose component is a directory symbolic link created between the check
  and a later read by name (needs the right to create symbolic links);
* control characters from session files in console output (F-03), the self-exclusion parent chain (F-06), installer
  verify-then-copy (F-07), the post-install `cmd.exe` lookup (F-13);
* `verify` and the installer bootstrap load code before checking it (R-B5), update and rollback atomicity (R-B6);
* `clean -LogFile` appends by name (F-04, latent: deletion is disabled), TEMP base attribution between users (F-05),
  and the deletion-engine documentation about share modes (F-10, latent).

These are fixed or tracked in V0.2.

## Install and verify

1. Download `agent-temp-manager-0.1.1.zip` and `SHA256SUMS.txt` from the GitHub Release `v0.1.1`; compare
   `(Get-FileHash .\agent-temp-manager-0.1.1.zip -Algorithm SHA256).Hash` with `SHA256SUMS.txt`.
2. Extract into a folder only administrators can write.
3. From an elevated PowerShell started with `-NoProfile`: `install\Install-AgentTempManager.ps1 -Update` over 0.1.0
   (or without `-Update` for a new installation). `install\Restore-AgentTempManagerPrevious.ps1` returns to 0.1.0.
4. Open a new terminal: `agent-temp verify`, `agent-temp version` (shows `0.1.1`).

## Validation evidence

Recorded in the hotfix pull request: test suite on Windows PowerShell 5.1 and PowerShell 7 (CI); real installation,
update from the published 0.1.0, rollback, audit export through the new writer, standard user and uninstall on
disposable Windows Server 2025, Windows Server 2022 and Windows 11 ARM64 VMs, installer under PowerShell 5.1 and 7.
